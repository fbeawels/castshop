# v1.1.4-TO-v1.1.5.sql

## Review

## 1. Summary  
The script is a **database migration** that upgrades an Oracle schema from version **1.1.4 → 1.1.5**.  
It performs the following tasks:

| Task | Description |
|------|-------------|
| **DDL changes** | Adds six new columns to `MERCHANT_USER_INFORMATION` to store security questions and answers. |
| **DML changes** | Removes a specific role definition, inserts four new role definitions, and updates the `CENTRAL_FUNCTION` table to associate function rows with the newly created roles. |
| **Environment** | Sets the session date format (`NLS_DATE_FORMAT`) to a specific layout. |

Key components are the `ALTER TABLE`, `DELETE`, `INSERT`, and `UPDATE` statements.  
The script relies on Oracle’s SQL dialect; no external frameworks or libraries are involved.

---

## 2. Detailed Description  

### Execution Flow  
1. **Session Configuration**  
   - `ALTER SESSION set NLS_DATE_FORMAT = 'YYYY-MM-DD HH24:MI:SS';`  
   Sets the default string format for dates throughout the session.  
   (This has no effect on the data being modified by the migration.)

2. **Add Columns**  
   ```sql
   ALTER TABLE MERCHANT_USER_INFORMATION ADD <column> VARCHAR2(64 CHAR);
   ```  
   Six columns (`SECURITY_QUESTION_1`, …, `SECURITY_ANSWER_3`) are appended.  
   All columns are variable‑length character fields with a maximum of 64 **CHAR** units, guaranteeing a fixed width in multi‑byte environments.

3. **Role Table Maintenance**  
   - Delete the role definition with `role_code='seller'`.  
   - Insert four new rows (role IDs 3‑6) all with the description “Store operator”.  
   These rows establish four distinct roles that the application will later use.

4. **Update Central Functions**  
   - Add a new `ROLE` column (`VARCHAR2(32 CHAR)`) to the `CENTRAL_FUNCTION` table.  
   - Assign role names to existing central functions via `UPDATE` statements.  
   The mapping is based on either `CENTRAL_FUNCTION_ID` or `CENTRAL_GROUP_CODE`.

### Assumptions & Constraints  
- **Idempotence**: The script assumes it will be run **once**. Re‑running it will fail because columns already exist or unique constraints on `role_code` may be violated.  
- **Foreign Key Integrity**: No constraints are added; it is assumed that `role_code` in `CENTRAL_FUNCTION` will later be enforced by application logic.  
- **Transaction**: The script is not wrapped in a transaction block, so partial application (e.g., if a `DELETE` fails) will leave the database in an inconsistent state.  
- **Role ID Mapping**: The same description is used for all four roles; this may be intentional or an oversight.  

### Architectural Notes  
- The script is purely **DDL + DML**; it is not part of a larger migration framework (e.g., Flyway, Liquibase).  
- The `ALTER SESSION` line is extraneous for a migration script and could be removed unless date formatting is needed for subsequent operations.

## 5. Additional Notes

### Edge Cases & Issues  
1. **Idempotency** – Re‑executing the script will fail when attempting to add columns that already exist or inserting duplicate `role_code` values.  
2. **Missing Transaction Control** – If any statement fails, earlier changes remain, potentially leaving the database partially upgraded.  
3. **Duplicate `UPDATE`** – `update CENTRAL_FUNCTION set ROLE='checkout' where CENTRAL_GROUP_CODE='CHK';` appears twice; the second is redundant.  
4. **Role Description Redundancy** – All four new roles share the same description (“Store operator”), which may be confusing for downstream code that relies on description uniqueness.  
5. **No Constraints or Indexes** – The script does not create foreign keys or indexes on the new `ROLE` column, which could impact performance or data integrity.  
6. **Missing `CHAR` vs `BYTE`** – Using `CHAR` ensures a fixed width in multibyte locales but may waste storage if most data is shorter.  

### Suggested Enhancements  
- **Wrap in a PL/SQL block with `COMMIT` / `ROLLBACK`** to ensure atomicity.  
- **Check existence before adding columns** using dynamic SQL or a `BEGIN ... EXCEPTION WHEN DUP_VAL_ON_INDEX THEN NULL; END;` pattern.  
- **Add foreign‑key constraints** linking `CENTRAL_FUNCTION.ROLE` to `MERCHANT_USER_ROLE_DEF.role_code`.  
- **Introduce indexes** on the new `ROLE` column if lookups are frequent.  
- **Remove or comment out the redundant `UPDATE`** statement.  
- **Add version‑control metadata** (e.g., `-- Version 1.1.5`) to aid future migrations.  
- **Consider a migration framework** (Flyway, Liquibase) for better tracking, rollbacks, and idempotence.

Overall, the script is straightforward but would benefit from safeguards that prevent accidental re‑application and ensure the database remains in a consistent state after migration.
