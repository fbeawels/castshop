## 5. Additional Notes  

### Edge Cases & Limitations  
- **Null `attributes`**: If the calling code expects a non‑null array, it may lead to `NullPointerException`. Consider initializing to an empty array.  
- **Invalid values**: Negative `quantity` or `price` could propagate into downstream calculations. Validation is absent.  
- **Array mutability**: The returned array from `getAttributes` can be modified by the caller, inadvertently changing the internal state. Defensive copying or an immutable collection would mitigate this.  
- **No `equals`/`hashCode`/`toString`**: Equality semantics are based on object identity, which may be insufficient for value‑based comparisons or logging.  

### Potential Enhancements  
1. **Immutable DTO** – Replace setters with constructor injection or use a builder pattern.  
2. **Collection for attributes** – Switch to `List<Attribute>` for flexibility and easier serialization.  
3. **Validation** – Add annotations (`@NotNull`, `@Min`, etc.) or explicit checks.  
4. **Utility methods** – Implement `equals`, `hashCode`, and `toString` for debugging and collection usage.  
5. **Documentation** – Javadoc comments for each field and method to improve maintainability.  
6. **Serializability** – Explicitly implement `Serializable` if the object is transmitted via Java serialization.  

### Future Extensions  
- **Pricing logic**: Methods to compute total price (`quantity * price`) or to apply discounts.  
- **Attribute handling**: Helper methods to retrieve an attribute by name or to filter attributes.  
- **Integration with a product catalog**: Linking `productId` to richer product metadata.

Overall, the `Product` class is a straightforward DTO suited for web‑service data transfer. Minor refactors (immutability, validation, collection use) would make it more robust and future‑proof.
